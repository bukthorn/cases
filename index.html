Redesigning a Data Import Workflow

I redesigned a high-risk import scenario in complex B2B software by analyzing recurring user mistakes, improving workflow logic, adding validation and warning scenarios, and delivering changes that made the import process safer and clearer for users.

ProblemRecurring support tickets over import errors
ArtifactsWorkflow map · Decision map · Roadmap
Outcome−20% related support requests
View full case Collapse case
Context

The product is a complex B2B platform for loading, analyzing, and interpreting spatial geological data. A critical workflow required users to import well-related spatial data before they could continue working with it in the project.

The import step was important because incorrect data positioning could affect downstream analysis. Users needed the system to guide them through the import process and prevent configuration mistakes before they propagated into later workflows.

Core problem
  • Users sometimes imported data incorrectly because the import template was configured in the wrong way.
  • Text labels and explanations were not clear enough for a high-risk import step.
  • Recurring support requests showed that the problem was not isolated — it was one of the common reasons for questions at this workflow stage.
Analysis

From repeated support requests to product decisions

02

Launching a New Data Analysis Algorithm from Scratch

I led the full product cycle for a new algorithm — from a client request and competitive analysis through UX design and release — delivering a capability that allowed users to extract new insights from existing data using an approach not previously available in the product.

ProblemNo equivalent algorithm in the product
ArtifactsCompetitive analysis · Parameter map · Journey map
OutcomeNew algorithm delivered from zero
View full case Collapse case
Context

The product is a complex B2B platform for loading, analyzing, and interpreting spatial geological data.

A key client requested a specific analytical capability available in competing products — one that allows users to extract insights from data that are not visible through standard analysis. The request came through the sales and business development team and carried potential commercial significance.

Core problem
  • The product had no equivalent of the requested algorithm, and it was unclear what the right scope and feature boundaries should be.
  • Competing products implemented the algorithm differently — with varying input requirements, calculation settings, and output formats — making it non-obvious which approach to follow.
  • An early internal version of the algorithm exposed too many configuration parameters, which users could not navigate without confusion.
  • Porting the calculation logic to the product's technical stack introduced implementation complexity that required ongoing coordination.
Analysis

Competitive analysis: defining the right scope

Before designing anything, I needed to understand how this algorithm existed in the market — what inputs it required, what settings it exposed, how fast it calculated, and what users received as output. I reviewed competing products directly where access was available, and studied technical documentation where it was not.

What I compared
What I found
What it led to
Input requirements across products
Products differed in what data types and formats were accepted as input
Defined clear input requirements for our implementation
Available calculation settings
Some products exposed many parameters; others had almost none
Established a baseline of settings that made sense to expose
Output formats
Outputs varied significantly in how results were presented to users
Defined output format based on what was most interpretable
Calculation speed
Performance varied considerably across products
Set expectations with the team and flagged speed as a constraint

Simplifying the interface: from too many settings to a workable UX

To decide what to keep, hide, or automate, I ran the calculations myself to see which parameters meaningfully changed the output, compared our settings against competitors, and tested the interface with users to identify what caused confusion. This reduced the visible configuration to a set users could work with confidently.
